# 开发流程（分支 / 部署 / 合并）

本文档定义 kiro2cc-proxy 的日常开发流程。**所有改动一律走分支 → 部署验证 → 合并主线**，禁止直接在 `master` 上开发或提交。

## 1. 分支规则

### 1.1 命名

从最新 `master` 切出，一个分支只做一件事：

```
feat/<简短英文描述>      新功能        例：feat/model-alias-config
fix/<简短英文描述>       缺陷修复      例：fix/sse-usage-drift
refactor/<描述>          重构          例：refactor/token-manager-lock
chore/<描述>             杂务/构建/文档 例：chore/bump-v3.4.34
```

### 1.2 开工

```powershell
cd E:\project\kiro2cc-proxy
git checkout master
git pull --ff-only origin master      # 必须以最新主线为基
git checkout -b feat/xxx
```

### 1.3 硬性约束

- **禁止**在 `master` 上直接 commit / push。
- **禁止**在服务端修改源码（包括"顺手改一行试一下"）。服务器上验证出的修复，必须回到本地分支改，再重新推送部署。
- 一个分支只解决一个主题；发现自己跑偏了，先合并或废弃，再开新分支。
- 分支存活期尽量短，验证通过即合并（§4），不攒大分支。

## 2. 服务端初始化（已完成，无需重复）

服务端已按"源码目录与数据目录分离"约定初始化完毕：

- `/opt/kiro2cc-proxy-src` — git 工作区，`origin` = `https://github.com/aidenli/kiro2cc-proxy.git`
- `/opt/kiro2cc-proxy` — 二进制 + 运行数据

历史坑（已修，勿重犯）：

- 该目录原先 `origin` 指向 `TsinHzl/kiro2cc-proxy`（上游作者的仓库），HEAD 停在 v3.4.15 的 `9c3b8a6`，与本项目主线 `aidenli/kiro2cc-proxy` 完全不是一条历史线。已 `git remote set-url origin` 切回本项目并 `git checkout -B master origin/master` 对齐到主线。
- 旧版仓库布局残留的 `admin-ui/`、`user-ui/`（各约 150M，含 node_modules/dist）已删除，前端统一走 `web-ui/`。

若日后重建该目录：

```bash
git clone https://github.com/aidenli/kiro2cc-proxy.git /opt/kiro2cc-proxy-src
# 校验 remote 必须是 aidenli，不是 TsinHzl
git -C /opt/kiro2cc-proxy-src remote -v
```

两个目录的职责永久分离：

| 目录 | 内容 | 谁可以改 |
|------|------|----------|
| `/opt/kiro2cc-proxy-src` | git 工作区、`target/`、`web-ui/*/dist/` | 部署脚本，通过 `git checkout -B` 强制覆盖 |
| `/opt/kiro2cc-proxy` | 二进制 + `config.json` / `credentials.json` / `api_keys.json` / `*_usage.json` 等运行数据 | 只替换二进制，**数据文件永不删除** |

> 之所以不再"删掉整个目录重新 clone"：数据目录里有账号凭据和全部 API Key 用量，删除即丢失线上配置。分离后重建源码目录不会碰到任何数据。

## 3. 部署流程

### 3.1 本地：提交并推送分支

```powershell
cd E:\project\kiro2cc-proxy

# 提交前自检（缺一不可）
cargo fmt
cargo clippy --all-targets
cargo test

git add -A
git commit -m "feat: 中文描述"
git push -u origin feat/xxx

# 记下要部署的提交，部署后用于核对
git rev-parse HEAD
```

前端有改动时，本地先跑一次 `cd web-ui/admin-ui; npm run build` 与 `cd web-ui/user-ui; npm run build`，确保 TS 能过——服务端构建失败会中断部署。

> **纯文档改动可跳过构建**：若分支只改了 `docs/`、`README*`、`CLAUDE.md`、`openspec/` 等不参与编译的文件（可用 `git diff --name-only origin/master...HEAD` 确认全部命中该范围），服务端只需 `git checkout -B` 对齐分支并确认 `git log -1` 与本地 sha 一致，**不构建、不替换二进制、不重启服务**，验证项简化为服务仍 `active` 且 `https://cld.gdapi.xyz/v1/ping` 返回 200。除此之外的任何改动（含前端、Cargo、src）都必须完整走 §3.2。

### 3.2 服务端：拉分支 → 构建 → 替换 → 重启

在服务端执行（把 `BRANCH` 换成实际分支名）：

```bash
set -euo pipefail
BRANCH=feat/xxx
SRC=/opt/kiro2cc-proxy-src
DATA=/opt/kiro2cc-proxy
export PATH="$HOME/.cargo/bin:$PATH"

# 1) 强制对齐远程分支（丢弃服务端任何本地改动）
cd "$SRC"
git fetch origin --prune
git checkout -B "$BRANCH" "origin/$BRANCH"
git log --oneline -1                 # 核对与本地 git rev-parse HEAD 一致

# 2) 前端（必须在 cargo build 之前，release 模式 rust-embed 编译期内嵌 dist）
cd "$SRC/web-ui/admin-ui"
npm install --registry https://registry.npmmirror.com --no-audit --no-fund
npm run build
cd "$SRC/web-ui/user-ui"
npm install --registry https://registry.npmmirror.com --no-audit --no-fund
npm run build

# 3) Rust release 构建
cd "$SRC"
cargo build --release
"$SRC/target/release/kiro2cc-proxy" --version   # 二进制能跑再替换

# 4) 备份旧二进制 + 原子替换（运行中的可执行文件不能 cp 覆盖，会 ETXTBSY）
TS=$(date +%Y%m%d-%H%M%S)
cp -a "$DATA/kiro2cc-proxy" "$DATA/kiro2cc-proxy.bak-$TS"
install -m 755 "$SRC/target/release/kiro2cc-proxy" "$DATA/kiro2cc-proxy.new"
mv -f "$DATA/kiro2cc-proxy.new" "$DATA/kiro2cc-proxy"

# 5) 重启
systemctl restart kiro2cc-proxy
```

耗时参考：首次 3~5 分钟（npm install ~1.5 分钟 + cargo 全量 ~2 分钟），之后增量 1~2 分钟。

### 3.3 验证（不通过禁止合并）

```bash
# a) 进程活着
systemctl is-active kiro2cc-proxy

# b) 端口探活，必须 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5678/v1/ping

# c) 无 panic / 无启动错误
journalctl -u kiro2cc-proxy -n 50 --no-pager

# d) 管理后台可访问（未授权时应为 200 静态页）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5678/admin

# e) 本次改动相关的功能验证（真实发一次请求，如 /v1/messages 流式，
#    或打开 https://cld.gdapi.xyz/admin 点一遍改动涉及的页面）

# f) 外网入口通（nginx 反代链路，返回 200 才算真通）
curl -s -o /dev/null -w "%{http_code}\n" https://cld.gdapi.xyz/v1/ping
```

同时核对二进制版本/时间戳：

```bash
/opt/kiro2cc-proxy/kiro2cc-proxy --version
ls -l --time-style=full-iso /opt/kiro2cc-proxy/kiro2cc-proxy
```

### 3.4 回滚

任何一项验证失败：

```bash
TS=<出问题的那次时间戳>
systemctl stop kiro2cc-proxy
mv -f /opt/kiro2cc-proxy/kiro2cc-proxy.bak-$TS /opt/kiro2cc-proxy/kiro2cc-proxy
systemctl start kiro2cc-proxy
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5678/v1/ping
```

回滚后回到本地分支修复，重新走 §3.1。**不要在服务器上直接打补丁。**

## 4. 合并主线

只有 §3.3 全部通过后才合并：

```powershell
cd E:\project\kiro2cc-proxy
git checkout master
git pull --ff-only origin master
git merge --no-ff feat/xxx -m "merge: feat/xxx"
git push origin master

# 清理分支
git branch -d feat/xxx
git push origin --delete feat/xxx
```

推送 `master` 会触发 GitHub Actions：`test.yaml`（全量测试 + 覆盖率）与 `docker-build.yaml`（构建并推送 `ghcr.io/...:beta` 镜像）。CI 挂了要立刻在 `master` 上开 `fix/` 分支修，不能放着。

> 发布 tag 另有一套强约束（版本号 + changelog 同步），见 `CLAUDE.md` / `openspec/project.md`，与日常分支流程无关。

## 5. 禁止事项

1. 禁止在 `master` 上直接改代码、提交、推送。
2. 禁止在服务端直接改源码 / 打补丁 / `git commit`。
3. 禁止 `rm -rf /opt/kiro2cc-proxy`（数据目录）。
4. 禁止把服务端的 `config.json`、`credentials.json`、`api_keys.json`、`*_usage.json`、`ip2region_v4.xdb` 提交回仓库（已在 `.gitignore` 中）。
5. 禁止用 `cp` 覆盖运行中的二进制（`Text file busy`），必须 `install` + `mv`。
6. 禁止跳过验证直接合并。
7. 禁止在服务端使用 pnpm（未安装）；前端一律 `npm --registry https://registry.npmmirror.com`。
8. 禁止在服务端执行 `docker compose up --build`（内存/磁盘不够，见 §6）。

## 6. 常见坑

| 现象 | 原因 / 处理 |
|------|-------------|
| 构建报找不到 `web-ui/*/dist` | release 模式 rust-embed 编译期内嵌，必须先构建两个前端 |
| 替换二进制报 `Text file busy` | 运行中的可执行文件不能原地覆盖，用 `install` + `mv` |
| `cargo: command not found` | 非交互 SSH 未加载 `~/.cargo/env`，先 `export PATH="$HOME/.cargo/bin:$PATH"` |
| npm install 极慢 / 卡住 | 漏了 `--registry https://registry.npmmirror.com` |
| 服务端代码和本地不一致 | 只可能是漏了 `git reset --hard origin/$BRANCH`；永远以远程分支为准 |
| 磁盘告警（`/` 已用 ~86%） | 每次构建 `target/` 约 500M；定期 `cd /opt/kiro2cc-proxy-src && cargo clean`，并清理 `/opt/kiro2cc-proxy/` 下多余的历史二进制（只保留当前 + 最近 1 个 `.bak-*`） |
| 部署后功能没变化 | 忘了 `systemctl restart`；或前端 dist 是旧产物（先 `rm -rf web-ui/*/dist` 再构建） |

## 7. 给 AI 助手的执行约定

每次接到开发任务，按此顺序执行并在回复中报告结果：

1. **开分支**：确认 `master` 干净并同步远程，切 `feat/` 或 `fix/` 分支；先说明分支名再动手。
2. **开发**：改动局限在最小必要范围；行为变更同步补内联单元测试；提交前 `cargo fmt` + `cargo clippy` + `cargo test` 全绿。
3. **推送**：Conventional Commits + 中文提交信息，推送到 `origin/<分支>`，报告 commit sha。
4. **部署**：按 §3.2 在 `gdapi` 上执行，部署前核对服务端 `git log -1` 与本地 sha 一致，部署后执行 §3.3 验证并把结果（HTTP 状态码、服务状态、日志关键行）贴出来。
5. **合并**：只有验证全绿才合并 `master` 并删除分支；任何一项失败则回滚并报告阻塞原因，**不得合并**。
6. 涉及线上配置（账号、Key、额度）的操作一律先说明再执行，不擅自改动数据目录。
